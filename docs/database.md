# Каталог и данные пользователей в Supabase

Проект `ssahtncunusgptkrkxkj`. SQL хранится в `supabase/migrations/`.

| Таблица | Назначение |
| --- | --- |
| `dishes` | Название, короткое описание, время в минутах, URL картинки, тип приёма пищи, теги, специи, базовые порции |
| `dish_steps` | Блюдо, порядок (с 1), описание, длительность в секундах, совет, один nullable URL картинки |
| `ingredients` | Фиксированный справочник, описание, категория, единица, цены, аллергены, пищевые признаки, КБЖУ |
| `dish_ingredients` | Многие ко многим: блюдо, ингредиент, количество, единица, порядок |
| `profiles` | ID из `auth.users`, приложение входа, ID провайдера, логин и имя; синхронизируются из доверенных app metadata |
| `cooking_history` | Отдельный UUID на каждое приготовление, пользователь, блюдо, дата, nullable оценка 1–5 |
| `catalog_settings` | Вспомогательные акции и словарь калорий для текущего интерфейса |

У блюда минимум один шаг; это проверяется отложенным ограничением в конце транзакции.
Номер шага уникален внутри блюда. Один ингредиент входит в блюдо один раз.
Количество ингредиентов относится к базовому числу порций (`servings`, при импорте 4).
КБЖУ в порядке `[ккал, белки, жиры, углеводы]`: на 100 г/мл или на единицу.
`duration_seconds=0` в исходных шагах означает отсутствие отдельного таймера,
а не измеренную нулевую длительность операции. Короткие описания блюд при импорте
формируются из названий первых трёх ингредиентов; авторских описаний в исходнике нет.

## Импорт и проверка

Node.js 24, секрет окружения `SUPABASE_ACCESS_TOKEN` (Personal Access Token).
При необходимости задать `SUPABASE_PROJECT_REF`; по умолчанию указан текущий проект.

```sh
npm run db:plan       # только построить импорт и показать количество записей
npm run db:migrate    # применить новые SQL-миграции и повторяемый импорт
npm run db:verify     # проверить ограничения/RLS, все тестовые записи откатить
```

Если сеть требует HTTP(S) proxy, добавить `NODE_USE_ENV_PROXY=1`.
`npm start` только запускает API и не изменяет базу, даже если задан
`SUPABASE_ACCESS_TOKEN`. Миграции и импорт выполняются отдельно: через
`npm run db:migrate` или ручной workflow **Database migrate**. Сначала успешно
применить изменения базы и выполнить `db:verify`, затем деплоить зависимый от них backend.
При ошибке миграции команда и workflow завершаются с ошибкой; деплой продолжать нельзя.
PAT нужен только для управления базой, для обычного запуска API он не требуется.
Имена применённых миграций фиксируются в закрытой схеме `familymenu_internal`.
Применённые SQL-файлы не редактировать: изменения оформлять новой миграцией.

Исходный снимок: `backend/data/catalog.seed.json` — 175 блюд, 86 ингредиентов,
700 шагов, 930 связей блюдо–ингредиент. JSON используется **только для импорта и тестов**,
не включается в клиент и runtime-образ API. Импорт сохраняет исходные ID и все поля.
Повторный импорт обновляет исходные блюда, их шаги и состав; он не удаляет пользователей,
приготовления и дополнительные блюда. После ручного редактирования исходных блюд
не запускать импорт без намерения восстановить значения снимка.

## Чтение приложением

Web / Android / iOS → `GET https://vibe-coding-sc04.onrender.com/api/catalog`
→ серверный Supabase RPC `get_catalog()` → нормализованные таблицы.
RPC возвращает каталог одним согласованным снимком, включая упорядоченные шаги
и ингредиенты, без обрезания вложенных списков лимитом PostgREST.
Backend кэширует успешный ответ на 60 секунд; провайдерские ошибки и ключи клиенту
не передаются. При ошибке приложение предлагает повторить загрузку, локального
резервного каталога нет. Полный production Web билд перед push не требуется;
он и браузерный сценарий выполняются CI.

732 исходных PNG лежат в `backend/public/art/`, публично доступны через
`/assets/art/<id>.png` и `/assets/art/<id>-step-<index>.png`. Это те же изображения,
без зависимости от доступности GitHub Pages приватного репозитория. URL хранятся
в таблицах. Одному шагу соответствует максимум одна картинка.

## Права

- `anon` и `authenticated`: чтение каталога; запись запрещена.
- `authenticated`: чтение только своего профиля; поля входа меняет backend после подтверждения Telegram.
- `authenticated`: чтение и изменение только своих записей `cooking_history`.
- Административный импорт: через Management API, токен не передаётся в приложения/CI.

Повторное приготовление одного блюда разрешено, оценка может отсутствовать.
Удаление блюда с историей запрещено внешним ключом; удаление Auth-пользователя
каскадно удаляет профиль и историю. UI использует реальную авторизацию. Текущее меню, отметки и предпочтения синхронизируются на пользователя; отдельный сценарий записи истории приготовлений и оценок в этой задаче не изменяется.

Для реальной проверки развёрнутого каталога: `node scripts/check-catalog-backend.mjs`.
Она читает каталог и несколько картинок, не отправляет фотографии в OpenAI.

## Личные аккаунты

Миграция `202610220003_user_accounts.sql` удаляет общий тестовый аккаунт и его запасы, закрывает старые test RPC и связывает `user_ingredients` с `auth.users`. Новые `user_preferences` и `user_menus` хранят текущие предпочтения и меню по UUID пользователя. История приготовления/оценок остаётся в `cooking_history`; новая история меню не создаётся.

`get_inventory`/`mutate_inventory` и `get_user_state`/`save_user_state` используют только `auth.uid()` из JWT. Клиентский ID пользователя не принимается. Функции доступны только `authenticated`, таблицы закрыты для прямого доступа, RLS включён. Меню и предпочтения обновляются одной транзакцией с ревизией, устаревшая версия возвращает 409. Общий аккаунт `test@test.com` не переносится в реальные учётные записи.

Вход в приложение — только через Telegram-бота. Миграция `202610220005_telegram_accounts.sql`
заменяет email в `profiles` на `login_application`, `provider_user_id`, `login`, `display_name`.
Уникальная пара приложение + ID провайдера определяет аккаунт; изменение username не меняет владельца.
Старые аккаунты и их данные сохраняются без автоматической привязки. Метаданные берутся только
из `auth.users.raw_app_meta_data`, клиентские `user_metadata` не задают личность.
Для стандартных JWT/refresh sessions Supabase Auth использует внутренний адрес
`telegram-<случайное значение>@auth.familymenu.invalid`: он не является пользовательской почтой, не показывается,
не сохраняется в `profiles`, на него не отправляют письма. Случайный адрес не позволяет
заранее занять чужую Telegram-личность через прежнюю регистрацию по email. Публичные email/password endpoints удалены.
Проверки: `supabase/tests/accounts.sql` и `supabase/tests/telegram.sql`, все тестовые изменения откатываются.

## Основные блюда и гарниры

Миграция `202610220004_main_side_dishes.sql` разрешает два новых типа `meal`: `p` — основное блюдо
(мясо, птица, рыба, растительный белок) и `g` — гарнир. Гарнир несёт тег `with:<фраза>`
(«с гречкой»), основное — теги `pair:gN` с рекомендуемыми гарнирами. Клиент собирает пару в одно
блюдо на лету: шаги гарнира идут первыми, затем шаги основного. В недельное меню эти типы не попадают.

Для совместимости со старыми выпущенными клиентами RPC запасов возвращает устаревшее
поле `userEmail` с пустой строкой; реальная почта в API запасов не передаётся.
